# /ana｜精實需求分析

## 原則
- 先閱讀適用的根目錄、Projects/ 與產品 CLAUDE.md；只讀必要檔案，不全面掃描。
- L0／L1 定義見根目錄 CLAUDE.md「知識層級」；查 L0 先看 `Shared/Tech/README.md` 再按需查閱，L1 以實際專案結構為準。
- 優先採用簡單、可維護、可驗證的方案；避免不必要的 Agent 往返與 Token 消耗。

## 分流
1. 釐清目標、影響範圍、驗收標準與主要風險；資訊足夠就直接評估。
2. **一般更新**：優先沿用 L0/L1 既有技術，提出最小實作與測試方式；既有技術不足時轉 `/hub` 研究。
3. **重大更新**（新核心功能、架構或關鍵技術替換、高風險資料操作）：查閱相關 L0/L1 知識，並依 `/hub` 的研究方法比較外部方案。若 `/hub` 可用則使用；不可用時明確說明，不假裝已執行。
4. 涉及重大產品決策、架構變更、權限或真實資料高風險操作，先取得使用者同意。
5. 按需交由 PO、Engineer、QA；不強制三者全部參與。未獲授權不得自行 Commit、Push 或執行破壞性操作。

## 輸出（簡短）
- **判定**：一般／重大更新，及理由。
- **方案**：現有技術或研究結果、主要風險。
- **任務**：2～5 個可驗收的小步驟；列出需要使用者決策的事項（若無則省略）。

## 結案知識閉環
- 僅在實際完成並通過必要 QA 驗證後，檢查是否有可重用的新知識；只收錄已驗證且跨專案可重用的內容。找到候選先列出給使用者決定，未經授權不自動擴大收錄範圍。
- 先搜尋相似知識；有則整合既有內容、保留適用差異，無則新增精簡條目。
- 跨產品知識寫入 `Shared/Tech/` 對應分類；產品專屬知識留在 L1 專案。分工：References＝技術原理、方法與實測經驗；Solutions＝已驗證解法（可含完整必要程式碼）；Snippets＝有獨立重用價值的小型程式片段。
- 同一段程式碼只存一處；測試腳本僅在有重跑價值時保留。
- 記錄問題、解法、驗證依據、適用條件與限制、未驗證範圍；必要時更新 `Shared/Tech/README.md`。未驗證不得標記為已驗證；單次量測（含效能數據）須標註測試環境，不得視為通用結論。
