# 影片編碼瓶頸分析與實測方法

> 狀態：方法已驗證；**數據僅限下列測試環境，不是通用結論**｜收錄：2026-11-08｜來源：個人研發產品（已去識別化）

## 問題
轉檔／合成太慢，但監控看起來 CPU、GPU 都沒用滿，不知道該調哪裡。直覺（「用不滿就加並行」「GPU 才 20% 還很空」）常常是錯的。

## 方法（可重用）
把管線拆開，**各段單獨量 fps**（fps＝影格數÷秒數），瓶頸就是最慢那一段：

1. **只解碼**：`ffmpeg -i src -f null -`（CPU 解碼），再加 `-hwaccel cuda`（NVDEC）。
2. **解碼＋濾鏡**（縮放、fps、格式轉換），不編碼：同樣輸出到 `-f null -`。
3. **完整管線**：實際用的編碼參數。
4. **掃描編碼預設**（例如 NVENC p5／p4／p3）：
   - fps **跟著提高** → 瓶頸在編碼，調預設有用。
   - fps **幾乎不變**，但編碼引擎使用率下降 → 瓶頸在前面（解碼、濾鏡或 I/O），調編碼預設沒用。
5. **同時取樣編碼引擎使用率**：`nvidia-smi --query-gpu=utilization.encoder,utilization.gpu --format=csv,noheader,nounits`，每 0.5 秒一次。
   - `utilization.gpu`（整體）算的是圖形／運算引擎，**不是**編碼引擎。整體 GPU 低、編碼引擎滿載是正常的，不代表還有餘裕。
6. **並行測試**：兩個同類工作同時跑，比較「合計吞吐」＝單獨做兩份的時間÷同時做的時間。接近 1.0 就是沒有收益。
7. **改預設後一定驗畫質**：用同樣濾鏡處理來源當參考，量輸出的 PSNR／SSIM，對照你的驗收門檻。

注意：
- 測試時 GPU 不能同時有別的真實工作，否則量到的是被占用的數據。
- 來源要有代表性。**錯誤示範**：我第一輪用了極高位元率（約 350 Mbps）的素材，變成解碼瓶頸，三個編碼預設一樣快（173～176 fps），差點得出「預設沒差」的錯誤結論；換成一般位元率（約 18 Mbps）後才看出差異。

## 實測數據（僅此環境）
**環境**：Windows 11 Pro（10.0.26200）；CPU 20 核心 2.50 GHz；NVIDIA GeForce RTX 4060 Ti 16 GB，驅動 621.01；FFmpeg 7.1（gyan.dev essentials build）。
**素材**：合成畫面（曼德博集合＋雜訊），**不是實拍影片**；1920×1080 60 fps、15 秒、約 18 Mbps（H.264）→ 輸出 2560×1440（CPU lanczos 縮放）、60 fps、yuv420p、無音訊、輸出 mpegts。每項**只量一次**，未重複取平均。
**NVENC 參數**：`h264_nvenc -rc vbr -cq 23 -b:v 0 -g 120`，加上預設——p5：`-preset p5 -tune hq -bf 3 -spatial-aq 1`；p4：`-preset p4 -tune hq -bf 3 -spatial-aq 1`；p3：`-preset p3 -tune hq -bf 2`。x264：`-crf 16`，preset medium／fast／veryfast。

**各段單獨量**

| 段 | fps |
|---|---|
| 只解碼（CPU） | 1518 |
| 只解碼（NVDEC） | 777 |
| 解碼＋CPU lanczos 縮放（不編碼） | 877 |

**完整管線（NVDEC 解碼）**

| 編碼 | fps | 相對 p5 |
|---|---|---|
| NVENC p5 | 197 | 1.00× |
| NVENC p4 | 266 | 1.35× |
| NVENC p3 | 378 | 1.92× |
| x264 fast（全部核心） | 82 | 0.42× |

**畫質與大小**（10 秒版本，PSNR／SSIM 對照同濾鏡處理的來源）

| 編碼 | 檔案 | PSNR | SSIM |
|---|---|---|---|
| NVENC p5 | 54.5 MB | 43.48 dB | 0.9927 |
| NVENC p4 | 54.7 MB | 43.48 dB | 0.9927 |
| NVENC p3 | 58.3 MB | 44.49 dB | 0.9924 |
| x264 medium | 60.6 MB | 45.43 dB | 0.9946 |

**其他**
- `scale_cuda`（GPU 縮放）lanczos：108 fps，比 CPU 縮放的整條管線還慢；bicubic：200 fps，與基準相同。→ 在這個環境把縮放交給 GPU 沒有好處。
- 兩個 NVENC 工作同時（p4）：合計吞吐 **1.04×**，等於沒有收益（高位元率素材那一輪量得）。
- NVENC p4 與 x264 fast 各一個同時：合計 **1.17×**。
- 在 1440p60 下，x264 單獨：medium 27.8、fast 36.2、veryfast 69.6 fps（高位元率素材那一輪）。

**這個環境的結論**：瓶頸是 NVENC 編碼預設，不是閒置的 CPU；調快預設有效、同時多做沒用、GPU 縮放沒用。

## 限制與尚未驗證
- 素材是合成畫面，**PSNR／SSIM 不等於實拍影片的觀感**；實拍的壓縮難度不同，倍數會不同。
- 只測 H.264、1440p60、15 秒短片、無音訊、單一來源；**沒有**測多段拼接（concat）、音訊處理、4K、HDR。
- 沒測 HEVC／AV1 的 NVENC，也沒測其他 GPU。**有兩顆編碼引擎的顯卡**，並行行為可能不同。
- 每項只跑一次，沒有量變異；長時間（數小時）的散熱降頻沒測。
- 「GPU＋CPU 同時」只測一個組合，倍數取決於 CPU 編碼有多慢，不能直接套用到別的設定。
